# Existing-user password enrollment command

The local-only management command `python scripts/set_user_password.py <email>` enrolls or replaces the local password credential for exactly one existing active user. It is not an HTTP endpoint and does not create users. Password input is accepted only through hidden `getpass` prompts; `GetPassWarning`, EOF, interruption, and other prompt failures abort before the enrollment service is called. The command never falls back to echoed input, stdin pipes, password arguments, environment variables, or configuration files.

Before changing anything, the command displays the resolved user ID/email and safe presence metadata for local password, OAuth, and MFA methods. The operator must type an exact confirmation phrase containing both the stable user ID and canonical email. The read-only lookup transaction ends before prompting. Mutation is bound to that profile's user ID; in a fresh transaction the service selects that exact user row `FOR UPDATE` (honored by MySQL/InnoDB), and fails closed if the row disappeared, became inactive, or its canonical email changed. It never re-resolves the email to select another user. Run only after identity proofing, explicit authorization, and a fresh protected backup, and verify the selected `DATABASE_URL` points to the intended database.

The command reuses `app.core.password_policy.validate_new_password()` and `app.core.security.hash_password()`. A mismatch, policy failure, inactive/unknown/ambiguous identity, or audit/database failure leaves the transaction uncommitted. It updates only `users.hashed_password`, revokes that user's refresh-token rows and session families, and writes a signed `admin_password_credential_changed` audit event in the same transaction. OAuth accounts, MFA state, identity fields, roles, licenses, and all other users are not changed.

Password replacement revokes refresh tokens, but this service's access JWTs are stateless and may remain usable until expiry unless a separate token-revocation mechanism is used. `ACCESS_TOKEN_EXPIRE_MINUTES` defaults to 15 minutes; it is configurable and has no hard maximum enforced by the current configuration, so the deployment's configured value determines the residual maximum lifetime. Do not claim immediate universal logout. The command does not make a production database backup itself and has not been run against production as part of its implementation.
